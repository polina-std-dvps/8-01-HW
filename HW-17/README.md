### Задание 1

Активный master + пассивный slave:
1. Отказоустойчивость: если master падает, slave повышается до master (failover), и потеря данных минимальна.
2. Простота: одна точка записи, нет конфликтов данных, настройка и сопровождение недорогие.
3. Бэкапы и миграции можно делать на slave, не нагружая рабочую базу.
4. Минус: slave простаивает, а чтение не масштабируется.

Master + несколько slave:
1. Масштабирование чтения: запросы SELECT распределяются между slave. Это выгодно, когда чтения намного больше записей.
2. Каждому slave можно дать свою роль: отчёты и аналитика, поиск, бэкапы. Основной нагрузке они не мешают.
3. Slave можно разместить ближе к пользователям, в другом дата-центре или регионе, и добавлять их без остановки системы.
4. Есть выбор кандидатов на роль нового master.
5. Ограничения: запись всё равно идёт через один master, а из-за асинхронной репликации возможно отставание (replication lag).

## Задание 2

![Скрин к 2му заданию 1]()


Вертикальный шардинг — разделение базы данных по таблицам. Каждая таблица размещается на отдельном сервере, что снижает нагрузку на каждый из них и позволяет масштабировать их независимо.

Горизонтальный шардинг — разделение одной таблицы по строкам. Наиболее объёмная таблица «Пользователи» делится между двумя серверами по чётности идентификатора user_id. Структура таблицы на обоих серверах одинакова, различается только набор записей.

Роутер (маршрутизатор). Приложение обращается не напрямую к серверам, а к роутеру, который по ключу запроса определяет нужный сервер.

Репликация master–slave. Для каждого сервера создаётся резервная копия (slave), которая синхронизируется с основным сервером (master).

Распределение данных по серверам: 
![Скрин к 2му заданию 2]()

Режимы работы серверов

1. Master каждого шарда работает в режиме read/write. Все записи (INSERT, UPDATE, DELETE) выполняются только на них.
2. Slave каждого шарда работает в режиме read-only и получает данные от master через асинхронную репликацию. Он отдаёт SELECT-запросы, служит источником для бэкапов и отчётов, а при сбое master заменяет его (failover). При росте чтения slave на шарде можно добавить.
3. Роутер / shard-map рекомендуется запускать минимум в двух экземплярах (основной и резервный) в режиме active-passive. Карту шардов лучше хранить в отказоустойчивом хранилище (etcd или ZooKeeper).
