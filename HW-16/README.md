### Задание 1

Master-Slave (однонаправленная)
1. Один сервер (master) принимает все записи (INSERT, UPDATE, DELETE). Он пишет изменения в бинарный лог (binlog).
2. Один или несколько серверов (slave) подключаются к master, читают binlog и применяют изменения к своим данным.
3. Чтение можно распределять между slave-серверами (балансировка нагрузки), но запись — только на master.
4. Если master упал, slave можно повысить до master вручную (или через оркестратор типа Orchestrator/MHA), но автоматический failover — это отдельная задача.

Master-Master (двунаправленная)
1. Оба сервера являются master одновременно: каждый принимает записи и реплицирует их на другой.
2. Теоретически даёт отказоустойчивость: если один упал, второй продолжает работать.
3. Главная проблема — конфликты: если на обоих серверах одновременно изменяют одну и ту же строку, возникает конфликт. MySQL не умеет разрешать конфликты автоматически (в отличие от, например, CockroachDB или Cassandra). Нужны дополнительные механизмы:
4. разнесение автоинкрементных ID (например, auto_increment_increment и auto_increment_offset на разных серверах, чтобы ID не пересекались);
5. разделение записей по таблицам/схемам (приложение пишет на один сервер, другой — в резерве);
6. внешние инструменты контроля конфликтов.
