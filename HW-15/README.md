### Задание 2

Узкие места: 
1.  Неявные JOIN через запятую (cross join + WHERE), Это устаревший синтаксис. MySQL сначала строит декартово произведение всех пяти таблиц, а уже потом фильтрует через WHERE. На больших таблицах это катастрофа по производительности. Современный JOIN ... ON позволяет оптимизатору выбирать порядок соединения и использовать индексы.
2. DATE(p.payment_date) = '2005-07-30' — функция на колонке убивает индекс
Оборачивание колонки в функцию DATE() делает условие non-sargable: MySQL не может использовать индекс по payment_date и вынужден сканировать всю таблицу. Нужно использовать диапазон:
3. В схеме sakila связь payment → rental идёт через payment.rental_id = rental.rental_id, а не через совпадение дат. Соединение по дате создаёт ложные совпадения: если два клиента арендовали фильмы в одну и ту же секунду, платежи привяжутся к чужим арендам. Это и логическая ошибка, и источник дублей.
4.  Отсутствует условие соединения inventory и film
В запросе пять таблиц, но условие i.film_id = f.film_id забыто. Без него каждая строка из inventory соединяется с каждой строкой из film (1000 фильмов × ~4580 копий = ~4,5 млн лишних строк). 
5. DISTINCT здесь нужен только потому, что неправильные соединения (пункты 3 и 4) порождают дубликаты. Если исправить соединения, DISTINCT становится не нужен.
6. SUM(p.amount) OVER (PARTITION BY ...) — оконная функция, которая вычисляет сумму по разделам, но не группирует строки: результат дублируется для каждой строки раздела. Отсюда и потребность в DISTINCT. Проще и эффективнее использовать GROUP BY.
7. Отсутствие индекса на payment.payment_date
В схеме sakila у таблицы payment есть индексы на rental_id, customer_id, staff_id, но нет индекса на payment_date. Без него фильтр по дате всегда означает полное сканирование таблицы.

### Задание 3

1. GiST (Generalized Search Tree). - позволяет реализовывать разные стратегии индексирования для сложных, нестандартных типов данных: геометрические объекты (точки, полигоны), диапазоны, полнотекстовый поиск, массивы. В MySQL для пространственных данных есть свои R-tree-индексы (через SPATIAL INDEX), но именно гибкой обобщённой инфраструктуры вроде GiST «из коробки» нет. 
2. SP-GiST (Space-Partitioned GiST). Это развитие идеи GiST: оно позволяет строить несбалансированные структуры данных на диске — например, деревья квадрантов (quadtrees), k-d-деревья. Это полезно для определённых сценариев пространственного поиска или работы с данными, которые естественным образом образуют кластеры. В MySQL такого аналога нет. 
3. GIN (Generalized Inverted Index). Этот тип идеален для индексирования составных значений. Например, он отлично подходит для полнотекстового поиска (когда вы индексируете текст через to_tsvector), для столбцов типа jsonb (чтобы быстро искать внутри JSON-объектов) или для массивов (когда в одном столбце хранится несколько значений). В MySQL нет прямого аналога GIN: для полнотекстового поиска там используются отдельные полнотекстовые индексы (FULLTEXT), а для работы с JSON — свои механизмы, но не инвертированный индекс в стиле GIN. 
4. BRIN (Block Range Index). Этот индекс эффективен для очень больших таблиц, где данные физически хранятся в порядке возрастания значений индексируемого столбца (например, временные ряды, логи, автоинкрементные ID). BRIN хранит не отдельные значения, а сводную информацию (минимум и максимум) для диапазонов блоков данных. Это делает индекс очень компактным, но он работает только при наличии естественной корреляции между физическим порядком строк и значениями в столбце.
